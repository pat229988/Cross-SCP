# CrossSCP Advanced Connection Scenarios

CrossSCP connects to an **effective host and port**. For simple sites that is
the remote server directly. For restricted networks, create the required network
path first, then point CrossSCP at the reachable endpoint.

## 1. Direct server, custom port

Use when the server is reachable from your machine.

1. Open **Sites**.
2. Select protocol: SFTP, SCP, FTP, or FTPS.
3. Set **Host** to the server name or IP.
4. Set **Port** to the server's custom port.
5. Leave **Advanced Connection** as **Direct host/port**.
6. Choose password or SSH key auth and connect.

Examples:

- SFTP/SCP: port `22`, `2222`, or another SSH port.
- FTP: port `21`.
- Explicit FTPS: usually port `21`.

## 2. Existing local tunnel / port forward

Use when another tool has already opened a local port, for example:

```bash
ssh -N -L 2222:internal-sftp.example.com:22 bastion.example.com
```

Then in CrossSCP:

1. Open **Sites**.
2. Set the real protocol, username, remote path, and authentication.
3. Set **Advanced Connection** to **Use existing local tunnel**.
4. Set **Tunnel Local Host** to `127.0.0.1`.
5. Set **Tunnel Local Port** to the forwarded local port, such as `2222`.
6. Connect.

CrossSCP will connect to `127.0.0.1:2222`; the SSH tunnel forwards traffic to
the real server.

## 3. SSH jump host / bastion host

CrossSCP can start an SSH local tunnel for jump hosts using your system `ssh`
client, then connect through that tunnel. You can authenticate to the jump host
with your SSH agent/key or enter a temporary jump-host password in the
**Jump Password** field. The password is not saved.

Example target:

- Final server: `internal-sftp.example.com:22`
- Jump host: `bastion.example.com:22`
- Local tunnel port: `2222`

Equivalent command:

```bash
ssh -N -L 2222:internal-sftp.example.com:22 user@bastion.example.com
```

In CrossSCP:

1. Select **SFTP** or **SCP**.
2. Enter your final-server username/authentication.
3. Set **Advanced Connection** to **SSH jump host via local tunnel**.
4. Enter the final server in **Host** and its port in **Port**.
5. Enter jump-host fields.
6. Optional: enter **Jump Password** if the bastion requires password auth.
7. Click **Connect**. CrossSCP starts the tunnel and then connects to the local
   forwarded port automatically.
8. If the automatic tunnel fails because of changed host-key confirmation,
   multi-factor prompts, or agent setup, run the displayed command in Terminal
   and use **Use existing local tunnel** instead.

## 4. Nested SSH hops / ProxyJump

Use this when the target service is behind two or more SSH hops, for example:

```bash
ssh -N -L 2222:127.0.0.1:1204 \
  -J heimdall@192.168.2.241 \
  heimdall@192.168.122.100
```

In CrossSCP:

1. Set **Host** to the service host as seen by the final SSH host, for example
   `127.0.0.1`.
2. Set **Port** to the service port as seen by the final SSH host, for example
   `1204`.
3. Set **Advanced Connection** to **Nested SSH hops / ProxyJump**.
4. Set **Tunnel Local Host** to `127.0.0.1` and **Tunnel Local Port** to an
   available local port such as `2222`.
5. Fill **ProxyJump Hop 1** with `heimdall`, `192.168.2.241`, port `22`.
6. Fill **Final SSH Host** with `heimdall`, `192.168.122.100`, port `22`.
7. Click **Manage Hops…** for the interactive hop builder. Add each SSH machine
   in order. Each hop can have its own username, port, private-key path, and
   password.
8. Fill **Final SSH Auth** separately if the final SSH host requires a different
   key or password than the jump hosts.
9. Click **Connect**. CrossSCP starts the nested tunnel and connects through the
   local forwarded port.

Equivalent command generated by the UI:

```bash
ssh -N -L 127.0.0.1:2222:127.0.0.1:1204 \
  -J heimdall@192.168.2.241 \
  -p 22 heimdall@192.168.122.100
```

## 5. VPN / private network

Use when the server is only reachable after a VPN connection.

1. Connect the VPN with your organization tool.
2. Confirm the server is reachable from Terminal, for example:
   `nc -vz server.example.com 22`.
3. In CrossSCP, use **Direct host/port** or the **VPN / private network**
   reminder mode.
4. Connect normally.

## 6. FTP/FTPS behind a jump host

FTP and FTPS use separate control/data channels, so SSH tunnels can be more
fragile than SFTP/SCP. Prefer VPN access when possible.

If your FTP server supports passive mode and a stable endpoint, try a tunnel to
the FTP control port:

```bash
ssh -N -L 2121:internal-ftp.example.com:21 user@bastion.example.com
```

Then connect with:

- Protocol: FTP or FTPS
- Advanced Connection: Use existing local tunnel
- Tunnel Local Host: `127.0.0.1`
- Tunnel Local Port: `2121`

If directory listing or transfer fails, the server's passive data ports are not
reachable through that simple tunnel. Use VPN or server-side passive port
configuration.

## 7. SOCKS/HTTP proxy

SOCKS/HTTP proxy support is documented as a scenario but not implemented in the
backend yet. Workarounds:

- Use a VPN.
- Use an SSH local tunnel.
- Use system/network tooling that exposes the destination as a local port.

## Current limitations

- Automated jump-host support is implemented through a managed local `ssh -L`
  tunnel. Native in-process ProxyJump is not wired directly into the Rust SSH
  backend yet.
- Jump-host password auth uses the system `ssh` askpass mechanism. The password
  is passed only to the child `ssh` process environment and is not stored in the
  saved site profile.
- The interactive hop builder supports mixed authentication, for example first
  hop by key, second hop by password, final SSH host by another password, and
  target SFTP/SCP service by the main site password.
- SCP is transfer-only: upload/download files, no browsing/mkdir/delete.
- Remote connect/list still uses a synchronous GUI bridge; an unreachable host
  or bad key can make the window appear stuck until the CLI timeout returns.
- Hardware-backed FIDO/U2F SSH keys depend on libssh2 support and may fail even
  when listed in the key picker.
